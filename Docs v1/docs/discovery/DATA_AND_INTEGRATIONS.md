## Observed architecture and database boundaries

The website has two related compatibility layers. Game features use configurable table/column constants and `Game/ServerModes`; CommerceCore has its own validated mapping, repositories, codecs, diagnostics and SQL connection contracts. The newer Universal Database layer performs discovery and semantic mapping and produces operation readiness. A replacement must reconcile these layers explicitly instead of assuming a single profile name certifies all operations.

## Observed storage, serialization and economy invariants

**Binary items:** 10/16/32-byte codecs are separate contracts. Serial numbers are decimal strings, not JavaScript numbers: the native allocator checks 32-bit maximum `4294967295` or 64-bit maximum `18446744073709551615` (`includes/commerce-core/Adapters/MssqlItemSerialProvider.php:25`). Empty slots use all `FF`; the 32-byte decoder explicitly handles that sentinel (`Hex32ByteCodec.php:32`). Preserve unknown bytes losslessly; opaque records cannot be transformed. Codec round-trip inspection and geometry resolution live at `includes/backend/src/Database/Universal/ItemCodecFramework.php:212` and `:355`. A round trip demonstrates codec consistency, not compatibility with a running vendor binary.

**Containers:** Identity includes account, optional owned character, container kind and vault number (`includes/commerce-core/Adapters/MssqlStorageContainer.php:18`). Inventory requires character identity; warehouses reject character identity. Reads require exactly one matching row and exact blob byte length; locked `pw` or blocked characters are rejected for mutation (lines 39–46). Writes compare the whole expected blob, use `CONVERT(varbinary(max), ?, 2)`, demand exactly one changed row, re-read the replacement and recheck offline status on the owning transaction (lines 48–63). Placement must use item rectangles and equipment offset, not a count of empty cells.

**Escrow:** `StorageService::reserve` owns one transaction; `reserveInTransaction` requires an existing owning transaction (`includes/commerce-core/Domain/Storage/StorageService.php:44`). Account serialization uses transaction-owned `sp_getapplock` at line 36. Reservation rejects zero serials, inserts the exact binary into the lock ledger and removes the source slot under CAS (lines 53–67). Delivery never allocates a new serial (`:86`); restoration uses the escrow item (`:146`). Global unique escrow serials and account/container/slot uniqueness are enforced in `includes/commerce-core/Migrations/001_core.sql:37`.

**Currencies:** Native balances are explicitly mapped; account and character ownership differ. `includes/commerce-core/Adapters/MssqlCurrencyProvider.php:35` resolves ownership, line 65 performs conditional adjustments with offline checks. Zen handling can span warehouse/character sources beginning at line 110, so a new system must not silently substitute a single website wallet. Confirm exact balance maxima, source priority and negative/overflow behavior with fixtures before migration.

**Serial allocation:** `MssqlItemSerialProvider.php:11` requires an owning transaction, verified writable adapter and independently approved native allocator; a website-only application lock is explicitly insufficient to prove safety against GameServer callers (line 15). The deployment registry is PHP source keyed by the exact routine-definition hash (`includes/commerce-core/Resources/serial-allocators.php:3`); do not promote a settings flag or routine name into approval. Stock Kayito's unguarded allocator is explicitly excluded there.

## Observed commerce and Workshop behavior

The generic coordinator commits debit and frozen outbox deliveries together. It hashes account, module, costs, deliveries and character; identical keys replay, changed payloads under the same key fail (`includes/commerce-core/Domain/Economy/TransactionCoordinator.php:38`). The ledger is read under `UPDLOCK,HOLDLOCK` at line 62. New item serials are server allocated; enqueue freezes bytes and targets (line 96). Delivery checks the stored mapping/catalog/codec/currency fingerprint and character ownership, writes one outbox item atomically, and records completion (line 257). Failure leaves the payload durable and stores a safe deferred code (line 284). Refund only permits undelivered debited transactions; partial delivery and consumed recipe escrow require reconciliation (lines 321–334).

Workshop uses `WorkshopService::execute` on one owning transaction for selected slots, escrow, recipe execution and frozen request evidence (`includes/commerce-core/Domain/Recipes/WorkshopService.php:145`). Request identity includes account, recipe, slots, character, role bindings and nonzero vault; replay checks the frozen request (`:96`, `:168`). Outcome generation is inside `TransactionCoordinator::executeRecipeInTransaction` (`:136`), with recipe/escrow locks, usage limits and immutable outbox output. Recipes support bounded rules and basis-point probability, not arbitrary formula evaluation; failure behavior is `BURN`, `DOWNGRADE_ZERO`, `DOWNGRADE_RANDOM`, or `KEEP` (`includes/commerce-core/Migrations/001_core.sql:95`).

The focused Workshop guide documents capacity validation before any random roll, success/failure space plans, frozen anchors, and delivery waiting when anchors become occupied (`dev/docs/WORKSHOP.md:55`). Newly produced reward items get fresh serials, while returned/unused inputs preserve original serials (`:34`). However, that guide says Workshop uses only the main warehouse (`:53`), while current `WorkshopService` accepts and fingerprints `vaultNumber`, exposes `vaults()` and reserves selected vaults (`:83`, `:145`, `:190`). Treat the actual allowed destination policy as unresolved until a focused source/fixture reconciliation.

**Player item market:** `MarketService::buy` locks the listing, rejects self-purchase, verifies private PIN, debits buyer, pays seller and places the escrowed item within its transaction (`includes/commerce-core/Domain/Market/MarketService.php:384`). Commission is floor(price × percentage / 100) and payout is price minus fee (`:161`). Preserve the original serial during resale. The important static gaps below mean the documentation's general phrase “atomic market” must not be copied into a new compatibility claim without narrower proof.

## Unresolved facts and observed source/documentation gaps

1. **No active deployment certification:** exact vendor/build, SQL version/collation, identity/password format, storage dimensions, extended-vault model, offline activity systems, online cache timing, currency mappings and allocator safety remain unknown in this audit.
2. **Universal readiness overstates allocator evidence:** `includes/backend/src/Database/Universal/CommerceCoreFusion.php:268` marks allocator `verified` if routine metadata was not checked, or a named routine/`GameServerInfo.ItemCount` exists. It does not equal the stricter exact-definition concurrency contract in `AbstractMssqlAdapter.php:36`. Its transaction readiness sets CAS true and bases status on mapped online fields (`CommerceCoreFusion.php:293`), which is structural evidence, not a concurrency test.
3. **Offline timing mismatch:** `MssqlOnlineStatusVerifier.php:14` does not reject zero status rows or null disconnect seconds; only non-null malformed timing is treated online (lines 15–27), and the function then returns false at line 51. This contradicts the guide's missing-timing fail-closed statement (`dev/docs/WORKSHOP.md:63`). Ambiguous multiple rows are also not explicitly rejected there. Preset grace is 60 seconds (`Presets.php:31`); the commerce guide says default 120 (`dev/docs/COMMERCE-CORE-2026-10-15.md:255`). No installed value was inspected.
4. **Market transaction boundaries:** listing calls self-contained `storage->reserve()` before beginning the listing INSERT transaction (`MarketService.php:174`, `:204`). Cancel/reclaim restore escrow before the later listing-state update (`:319`, `:328`, `:624`). Atomicity exists within each transaction, not across the entire documented lifecycle. Recovery and racing purchase/cancel scenarios need dedicated review.
5. **Market replay identity:** purchase replay checks only buyer account and `module=market`, then returns the caller-provided listing ID (`MarketService.php:393–412`); it does not compare the full requested listing/destination hash at that branch. A new contract should bind the full semantic request as the generic coordinator and Workshop already do.
6. **Workshop source drift:** current multi-vault source differs from main-warehouse-only documentation. Also, `dev/docs/WORKSHOP.md:75` records a broader CommerceCore aggregate assertion failure; historical focused test counts must not be reported as a fresh full aggregate pass.
7. **32-byte provenance:** fixed byte widths, approved layout IDs and synthetic round trips cannot certify vendor-specific semantics or unknown tail bytes. Deployment samples and isolated native integration are still required before mutations.

## Proposed Phase 2 contracts — design only

These are recommendations for ZendaMod-Next, **not implemented capabilities or authorization to integrate**:

| Proposed port | Required contract |
| --- | --- |
| `SchemaInspector` / `ProfileRepository` | Read-only metadata facts with fingerprint, provenance, ambiguity and revision. Separate draft, validated structural mapping, operation evidence and active deployment. Never auto-activate by name/confidence. |
| `CapabilityProvider` | Return per-operation state (`unsupported`, `blocked`, `read_only`, `structurally_verified`, `operationally_verified`), reason and evidence/version. Unknown/missing evidence denies writes. Readiness is advisory until the owning adapter rechecks current facts. |
| `AccountRepository` / `CharacterRepository` | Stable website ID separate from native username; exact password-format contract; ownership checked on every operation. Kayito identity stays additive without altering native tables. |
| `ItemCodec` / `CatalogRepository` | Versioned, deployment-evidenced codec/layout; raw bytes retained; lossless fixtures; serial as decimal string; dimensions, equipment header and option bounds explicit. No opaque writes or user-supplied generated serial. |
| `StorageRepository` / `OfflineGuard` | Full container identity; exact byte lengths; native lock enforcement; owned transaction and whole-blob CAS; exactly one owner/status row; absent/ambiguous/malformed timing fails closed; configured grace and off-trade/off-level guards explicit. |
| `SerialAllocator` | Independent reviewed native allocator proof for GameServer concurrency, exact definition fingerprint and width. Routine/table existence alone cannot enable synthesis. |
| `CurrencyRepository` / `UnitOfWork` | Explicit account/character scopes, limits, debit source order and conditional updates. Preserve single owning connection/session, checked transaction state, no hidden nested transaction or global shared connection. |
| `CommerceLedger` / `DeliveryOutbox` | Bind key to canonical full request; debit/escrow/outcome/frozen deliveries commit together. Replay never rerolls, reallocates serial or charges again. Retry preserves payload; partial delivery/refund reconciliation remains explicit. |
| `MarketService` / `WorkshopService` | Make lifecycle state and escrow transitions share one unit of work or a documented recoverable state machine. Compare full semantic replay payload. Validate space for all recipe outcomes before RNG. Distinguish fresh reward serials from returned-item serials. |
| `PaymentGateway` / `PaymentFulfillment` | Preserve provider-specific authentication, evidence ordering, amount/currency binding, transaction reuse prevention, retry/acknowledgment and reversals. Persist fulfillment before successful acknowledgment; browser returns cannot deliver rewards. |

Phase 2 can implement interfaces, inert/mock adapters and synthetic contract fixtures without connecting to legacy. Live reads/writes, SQL application, payment traffic, account testing, deployment activation and publication remain separate unexecuted work.
