## Disposition and sequence

**Rebuild** means independently implement requirements against the new contracts; **adapter** means preserve a public route/body/redirect through a small compatibility boundary; **retain external authority** means leave game-server data at its owner; **review/conditional** means no safe execution until schema/capability/rights evidence resolves the condition. These are plans subject to the architecture review. Shared responsibilities below identify ownership concepts; the canonical module names and interface signatures live in the new architecture/contracts documents.

The user requires review of the functional inventory, architectural contracts, workspace configuration and `STATE.md` after Phases 1–3. Stop at that gate. Phases 4–12 below describe future work and do not authorize starting it before the review response.

## Mandatory unknowns and release blockers

The focused [data and integration audit](DATA_AND_INTEGRATIONS.md) identifies current legacy gaps: weak allocator-readiness inference, missing/ambiguous offline-status handling, split market escrow/listing transitions, incomplete market replay binding and Workshop source/documentation drift. The new contracts must correct these gaps through fail-closed policies and tested state transitions. A general legacy claim of atomicity or compatibility is insufficient.

1. Approved non-production MSSQL environment, active game profile/custom mappings, observed schema and exact connection/driver requirements. No production/environment mutation is implied by connectivity.
2. Verified offline/synchronization protocol for each native writer, including independently running game servers, offline stores/attack, serial allocators and account/vault caches. SQL transactions alone are insufficient evidence.
3. Runtime activation/route parity for older modules and trusted plugins; current catalog/preset registration does not prove usage or write support.
4. Native identity/password/inventory/warehouse/progression mappings and fixture provenance, especially Kayito addons, S21 indices, SPK codec gates and Custom/SPK Mobile write support.
5. Rights/attribution for commercial custom work, game art, theme fonts/icons and `dev/WebShop Reference` examples. MIT WebEngine notice covers its licensed scope, not every nested item.
6. Payment sandbox evidence for exact provider signatures, callback status/body/retry/duplicate/refund handling and reconciliation of any existing undelivered transactions.
7. Website-owned data export scope, retention/privacy requirements, downtime/freeze window, rollback ownership, staged deployment environment and DNS/base-path decisions.
8. Explicit acceptance of the Phase 1–3 review package before any Phase 4+ feature implementation. Actual runtime, SQL, provider, visual and migration acceptance remains future work.
