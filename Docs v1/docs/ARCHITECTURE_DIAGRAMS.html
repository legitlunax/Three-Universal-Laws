1. Arquitectura actual Parcial

  • ZendaMod-Next
    • public/ · webroot
      • index.phpPunto de entrada HTTP
      • src/Bootstrap · composición estática
        • Router y handlersRutas y controladores compuestos por el kernel; no los registra un plugin runtime.
        • Plugins: descubrimiento de datosValida manifiestos/paquetes sin ejecutar código.
        • Aprobaciones y revisiónCimientos de persistencia/política; todavía sin activación HTTP de plugins.
      • src/Modules · módulos transicionales
        • IdentitySesiones y cuentas del sitio, perfiles web; no identidad nativa MU.
        • ContentAnuncios y lectura opcional de Drupal.
        • CommunityTickets de soporte del sitio.
        • GameDataGuías, eventos y proyecciones/previews sintéticos relacionados con MU.
        • AdminConfiguración web y herramientas administrativas.
        • TemplatesJSON canónico y renderizado de solo lectura; publicación deshabilitada.
        • Contratos V1–V5Superficies públicas congeladas/aditivas; no son el SDK MainAPI.
      • packages/premium/
        • Webshop y VIPPaquetes separados con catálogos y previews sintéticos; sin fulfillment nativo.
      • Persistencia web
        • MSSQL del sitioAdaptadores preparados por familia y evidencia de laboratorio acotada; no certifica producción ni todas las rutas.
        • Archivo / SQLitePrototipos offline y fixtures; no deben ser fallback silencioso del modo DB.
        • DrupalLectura anónima de noticias cuando se configura.

      • architecture/

No habilitado: escritura nativa MU, pagos/entrega de compras y publicación de plantillas. El runtime ejecutable de plugins y su ciclo HTTP añadir/quitar/reponer siguen pendientes.

2. Arquitectura objetivo Futura

  • ZendaMod-Next · kernel pequeño + plugins removibles
    • Kernel confiable
      • public/ y routerWebroot público y despacho HTTP.
      • Auth web / permisos / AdminCP baseAutoridad administrativa del sitio separada de las cuentas de juego.
      • MainAPI / PluginHost versionadaÚnica entrada de plugins; registro acotado, sin depender de carpetas opcionales.
      • MSSQL propio del sitioConfiguración, aprobaciones, migraciones revisadas, auditoría y datos persistentes.
    • Ciclo de vida de plugins/<vendor>.<slug>/
      • 1. DescubrimientoManifiesto/huellas de datos; sin ejecutar PHP al explorar carpetas.
      • 2. Confianza y compatibilidadAprobación, versión de API, dependencias, permisos y licencia.
      • 3. Registro por request/workerContribuciones presentes y aprobadas en una instantánea acotada.
      • 4. Remoción físicaRevoca rutas/superficies en el siguiente request; no borra los datos MSSQL.
      • 5. Reinstalación compatibleRevalida y puede reanudar estado retenido; no omite aprobación/migraciones.
      • Kernel vacíoEl sitio base/AdminCP puede arrancar con plugins/ vacío.
    • APIs de proveedores independientes
      • MainAPIRutas, eventos, servicios, AdminCP, jobs y widgets.
      • GameTypeAPIIdentidad/familia de juego y capacidades normalizadas (MU primero).
      • DatabaseTypeAPITransporte opcional de datos de juego; nunca provee el MSSQL del kernel.
      • SchemaAdapterAPIInterpretación validada del esquema/emulador, por ejemplo MUEMU o Louis.
    • Paquetes bajo plugins/
      • Proveedoreszenda.game.mu · zenda.db.mssql · zenda.schema.muemu como ejemplos objetivo.
      • Funciones gratuitasNoticias, rankings, perfiles y soporte como plugins independientes.
      • Funciones premiumWebshop, VIP, inventario y mercados en paquetes físicamente separados.
      • SuperficiesRutas, AdminCP, eventos, jobs, widgets y plantillas versionados.
    • Perfil de realm y datos separados
      • Perfil de realmAsocia juego + transporte + esquema exacto validado y topología.
      • MSSQL del sitioSiempre propiedad del kernel; independiente del plugin de transporte de juego.
      • Datos de cuentasOpcionales; pueden compartir la base de juego o estar separados.
      • Datos del juegoLecturas vía puertos normalizados; sin SQL nativo directo desde plugins de función.
      • TopologíaUna base unificada o almacenamiento dividido en varias bases.
    • Operaciones sensibles · siempre protegidas
      • Mutaciones MUPropiedad verificada, jugador offline, lock, recheck, idempotencia y auditoría.
      • PagosCallback verificado, protección de replay, valores inmutables y transición auditada.
      • PlantillasJSON canónico; preview privado; publicación bajo pipeline validado.
Dirección, no estado actual: migración gradual de módulos y paquetes existentes. APIs GameType, DatabaseType y SchemaAdapter aún son especificaciones; no describen runtime disponible hoy.
