## 2. Core System Identity, Tier-0 Invariants & Dual-Distribution Model

**ZendaMod-Next** (`C:/xampp/htdocs/ZendaWeb/ZendaMod-Next`) is a clean-room, modular PHP reconstruction of the legacy MU Online CMS (`C:/xampp/htdocs/ZendaMod`), designed to evolve from an initial **MU Online (`0.97d` to `Season 21`)** platform into a **multi-game Enjin-style CMS and visual website builder** supporting MU Online, Minecraft, Counter-Strike, Rust, Metin2, and Lineage 2 ([ZendaWeb Notebook](https://www.google.com/search?q=https%3A%2F%2Fgemini.google.com%2Fnotebook%2Fc7d7c8af-7969-48c5-8ad8-960dbcc36885)).

### Tier-0 Non-Negotiable Invariants

1. **Legacy Read-Only Isolation:** The original legacy installation at `C:/xampp/htdocs/ZendaMod` is strictly **READ-ONLY**. Never modify legacy files, execute legacy PHP scripts/installers/schedulers/tests, or copy installed secrets, licenses, player records, or third-party assets. Rely on static discovery artifacts (`FUNCTIONAL_INVENTORY.md`, `DATA_AND_INTEGRATIONS.md`, `MIGRATION_MATRIX.md`).

2. **Additive Contract Immutability (`V1`–`V5`):** Public interfaces under `src/Contracts/V1` through `src/Contracts/V5` and their cryptographic hash catalogs (`contracts/v1..v5/baseline.json`) are **frozen**. Never regenerate baseline hashes to mask a breaking change. Small internal improvements stay inside module `Application`/`Infrastructure` adapters; breaking cross-module changes require a new additive contract version (`V{N+1}` or `Zenda\PluginAPI\<Layer>\V1`) and explicit consumer migration.

3. **Fail-Closed Security & Mutation Gate:** Every unverified capability, ambiguous database schema, missing premium package, inactive license, or corrupt database state must fail closed with a clean, redacted private error (`503`/`422`/`403`) and **zero fallback to local disk files** when running in database mode. Native game mutations (`GameMutationGateway`), real-money payment fulfillment, and live template publication remain **disabled** until their dedicated concurrency, offline-verification, and validation pipelines are proven.

4. **Strict Realm & Identity Separation (`AdminCP` vs. `Player` vs. `Game`):** Website administrator credentials (`DDL 009`, `/admin/*`) and website player accounts (`DDL 010`, `/account/*`) occupy separate authentication, session, CSRF, and rate-limiter realms. An in-game GM flag (`CtlCode`), a matching player username, or a player role named `admin`/`GM` **never** grants AdminCP, installer, or schema-inspection authority.

5. **Authorization Precedes Lazy Connections:** Every application service must verify server-owned permissions via `V1.Authorization` **before** opening a lazy SQL connection, loading an optional package factory, or reading persisted state.

6. **Kernel Website MSSQL Independence:** Authoritative website state (settings, admin credentials, player accounts, templates, support tickets, market drafts, and plugin ledgers) resides in **website-owned MSSQL** (`WebsiteStore`) managed by the trusted kernel. It must operate with `/plugins` completely empty and **never** depends on the removable external game database driver (`zenda.db.mssql`).

7. **In-Process Trust Boundary:** PHP plugins execute in-process as **trusted, operator-approved code**, not a hostile-code OS sandbox. Security relies on data-only manifest scanning (`plugin.json` v1 without loading PHP), complete SHA-256 file inventory verification, explicit administrator approval in website MSSQL (`DDL 012`), and scoped registration handles (`PluginContext`) rather than exposing a global DI container or raw PDO connection.

## 3. Target Plugin-First Architecture & 4-Layer SDK Specification

Per `PLUGIN_SYSTEM.md`, `API_ARCHITECTURE.md`, and `Proposed Decision P105` ([ZendaWeb Notebook](https://www.google.com/search?q=https%3A%2F%2Fgemini.google.com%2Fnotebook%2Fc7d7c8af-7969-48c5-8ad8-960dbcc36885)), ZendaMod-Next's target architecture is a **single trusted kernel hosting four independently versioned plugin APIs**. Adding an approved `/plugins/<publisher>.<slug>/` directory activates its routes, menus, widgets, events, and capabilities on the next HTTP request; physically removing the directory immediately revokes all runtime contributions on the next request without deleting its retained MSSQL tables, settings, or audit history.

### The Four Independently Versioned Plugin APIs (`Zenda\PluginAPI\<Layer>\V1`)

Never conflate **Game Family** (`mu.online`), **External Database Engine** (`mssql`), and **Emulator Schema Layout** (`mu.emulator.muemu.s6`). Each is a distinct, independently removable provider bound explicitly per server realm in website-owned MSSQL:

| API Layer & Target Namespace | Core Responsibility & Scoped Interfaces | Strict Prohibitions ("Must Never Do") | 
| ----- | ----- | ----- | 
| **`MainAPI / PluginHost v1`**  `Zenda\PluginAPI\Main\V1`  Catalog: `contracts/plugin-api/main/v1/` | Entrypoint for **every** plugin via `PluginEntrypoint::register(PluginContext $ctx): void`. Provides scoped handles: `RouteRegistry`, `AdminExtensionRegistry`, `ServiceRegistry`/`CapabilityRegistry`, `EventBus`, `JobRegistry`, `CommandRegistry`, `WidgetRegistry`, `AssetRegistry`, `TranslationRegistry`, `SettingsAPI`, `StorageAPI`. | Never expose the raw DI container, root PDO connection, filesystem write access, or deployment secrets; never execute SQL, DDL, network calls, or mutations during `register()`; never allow route collisions or kernel route overrides. | 
| **`GameTypeAPI v1`**  `Zenda\PluginAPI\GameType\V1`  Catalog: `contracts/plugin-api/game-type/v1/` | Registers a game family (`GameTypeProvider::id()`, e.g., `mu.online`) and defines normalized gameplay concepts, realm validation (`validateProfile`), and permission-filtered read projections (`game.server.status.read@1`, `game.players.read@1`, `game.rankings.read@1`, `game.characters.read@1`, `game.guilds.read@1`, `game.items.catalog.read@1`). | Never hardcode SQL vendor queries in the kernel; never assume every game has MU resets/hex blobs; never expose raw native database tables to feature plugins; never auto-reassign a realm profile if its game provider folder is removed. | 
| **`DatabaseTypeAPI v1`**  `Zenda\PluginAPI\DatabaseType\V1`  Catalog: `contracts/plugin-api/database-type/v1/` | Registers **external game/account data transports** (`DatabaseTypeProvider::driverId()`, e.g., `mssql`, `mysql`, `pgsql`, `http`). Opens scoped, read-only `ExternalReadSession` (`inspectSchema`, `executeTypedRead(TypedQueryPlan): BoundedResultSet`) using server-owned connection profiles. | **Never** replace or supply the kernel's mandatory website-owned MSSQL (`WebsiteStore`); never accept DSNs/passwords from manifests or routes; never allow arbitrary raw SQL strings from feature plugins; never run DDL/writes during schema introspection. | 
| **`SchemaAdapterAPI v1`**  `Zenda\PluginAPI\SchemaAdapter\V1`  Catalog: `contracts/plugin-api/schema-adapter/v1/` | Registers verified emulator/layout mappings (`GameSchemaAdapter::id()`, e.g., `mu.emulator.muemu.s6`, `zenda.schema.louis`, `zenda.schema.xteam`). Runs `probe(ReadOnlySchemaInspector): SchemaProbeReport`, requires explicit `OperatorReview` (`validateMapping`), and binds `readPorts(VerifiedSchemaProfile)`. | Never guess or auto-select when 0 or $\ge 2$ adapters match; never claim universal Season 1–21 write support from table names alone; never write to native game tables during discovery; immediately revoke affected capabilities if schema fingerprint drifts. | 

### Canonical `plugin.json` v1 Manifest Specification (`Decision 104`)

Implemented in `src/Bootstrap/Plugins` as a strict **data-only** parser (`PLUGIN_MANIFEST.md`). Discovery scans direct child directories of `/plugins/<id>/` without loading or executing any PHP:

| Manifest Property | Exact Validation Constraint (`manifestVersion: 1`) | 
| ----- | ----- | 
| **`manifestVersion`** | Exact integer `1` (numeric strings rejected). | 
| **`id` & `publisher`** | `id` must match the exact directory name: lowercase dotted segments (`^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)+$`, max 96 bytes). `publisher` must equal the first segment (claim only, not cryptographic proof of provenance). | 
| **`name`, `version`, `distribution`** | `name`: 1–120 UTF-8 bytes, no control chars. `version`: strict `major.minor.patch` (`0`–`9999` per segment, no leading zeros, no prerelease/build tags). `distribution`: `"free"` or `"premium"`. | 
| **`contracts`** | Object requiring `mainApi: {min, maxExclusive}`; optional independent `gameTypeApi`, `databaseTypeApi`, `schemaAdapterApi` version range objects. | 
| **`requires`** | Object containing exact keys `php` and `core`, both `{min, maxExclusive}` release-version ranges. Evaluated at activation time. | 
| **`entrypoint` & `autoload`** | Canonical FQCN and exactly **one** top-level PascalCase PSR-4 namespace prefix mapped to `src/`. `Zenda` (in any case) is reserved for core. The case-exact entrypoint PHP file must exist in `files`. | 
| **`dependencies`** | Object with `required` and `optional` arrays (each $\le 32$ items of `{id, min, maxExclusive}`). No self-dependency, duplicates, or overlap between required and optional. | 
| **`providesCapabilities` / `requiresCapabilities`** | Up to 64 unique items each. `scope` is `"website"` or `"gameProfile"`. Profile-scoped capabilities require explicit server-selected realm binding (never first-match). | 
| **`permissions` & `contributions`** | `permissions`: $\le 64$ unique dotted IDs (requests only, never self-granted). `contributions`: subset of `routes`, `adminMenu`, `events`, `jobs`, `commands`, `assets`, `translations`, `widgets`, `services`, `settings`, `paymentGateways`, `gameTypes`, `databaseTypes`, `schemaAdapters`. | 
| **`providers`** | Up to 32 unique `{kind, id, version}` objects where `kind` $\in$ `{"gameType", "databaseType", "schemaAdapter"}`. Requires matching `contracts.<kind>Api` range and plural `contributions` entry. | 
| **`files`** | Map of 1–512 package-relative paths to lowercase 64-char SHA-256 hex digests covering **every** file in the package (PHP, views, assets, migrations, vendor libs) except root `plugin.json` (which is fingerprinted separately to avoid self-hash cycles). Symlinks, path traversal, case-folded duplicates, or extra unlisted files fail discovery immediately. |

## 5. Database Architecture, Website MSSQL Ledger (`DDL 001`–`013`) & MU Era Specs

### Three-Part Database Topology (`DATABASE.md` & `SKILL.md`)

ZendaMod-Next separates persistence into three logical realms that can be deployed in a **Single Unified MSSQL Database** (`MuOnline`), a **3-Way Physical Split** (`MuOnline` + `Me_MuOnline` + `ZendaWeb`), a **Shared Game/Account + Separate Web DB**, or **Multi-Realm Topologies** (`MuOnline_Realm1..N` sharing `Me_MuOnline` and `ZendaWeb`):
