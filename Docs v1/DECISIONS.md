# Architectural decisions

## Decision 112: derived URL and reusable Math operations (2026-10-20)

The user requested URL and Math derivatives to remove consumer hardcoding,
choosing reusable formulas starting with layout. Keep exactly three primary
APIs. Add isolated private Kernel/Urls and Kernel/Math Domain owners; Bootstrap
bridges pure url.resolve and math.evaluate 1.0.0 Singularity handlers into Order's
sealed registry. Chaos can propose these governed independent operations.
No frozen SDK, static module catalog or database schema changes.

Use named exact-version routes with closed path/query inputs and declarative
bounded arithmetic trees with input ranges. Reject external/traversal URLs,
unknown versions/fields, executable expressions, duplicate input names, division
by zero, nonfinite/coerced values and overflow. Neither owner depends on Order,
another kernel owner, SQL or transports. Resolving an admin URL grants no access.

The live builder consumes generated links/assets/save endpoints and server-supplied
layout formulas for snap/usable width; an equal-column formula is also available.
Trusted source declarations are application composition, not a file settings
fallback. Future editable catalogs require authoritative MSSQL, authorization,
revisions, audit and explicit version migration. Other site consumers, business
formulas, public SDK/plugin registration and whole-site mount support are pending.
See docs/api/URL.md, docs/api/MATH.md and STATE for actual checks and limits.

## Decision 111: self-hosted restricted live layout editor (2026-10-20)

The user authorized downloading and implementing the researched open-source
libraries. Pin GrapesJS 0.23.8, Material Color Utilities 0.4.0, Moveable 0.53.0
and Floating UI DOM 1.8.0 with npm integrity, a Vite build, retained notices and
artifact hashes. Serve compiled assets locally; no customer Node service or
commercial Studio SDK is required. Native Grid/Flexbox handle layout and wrapping.

Replace the public edit route's placeholder with a Templates-owned view/profile:
real canvas, nested layout blocks, spacing/width/alignment controls, Material
themes, live geometry, bounded resizing, responsive previews, page switching,
undo/redo and explicit draft saves. The new save route reuses separate admin
authorization, CSRF, origin/body limits and immutable TemplateStore/CAS semantics.
Materialize transient component IDs and keep styles in component state to retain
them through real undo/redo. Theme identity is undoable canonical model data.
Save status compares submitted/current canonical data to retain in-flight edits.

Use a bounded plain-content profile before loading or saving, escaped host
configuration, editor-scoped CSP and a canvas sandbox without script permission.
Dedicated GrapesJS text nodes preserve literal text via textContent/escaped
export; raw HTML content in other types refuses. Checked inline style attributes
and objects use the same declaration profile. This is not a general sanitizer.
Dynamic existing V1 types remain synthetic placeholders. Publication, optional
provider blocks, complete editor features and actual MSSQL template cutover stay
pending. Frozen V1-V5/catalogs/old fixtures and SQL schemas remain unchanged.

PHP profile/artifact tests, a real captured project, JavaScript units and owned
Chromium HTTP geometry/security/round-trip cases verify this restricted slice.
Existing static application boundaries remain; Order's private read profile is
not expanded into a write executor. See docs/LIVE_BUILDER.md and STATE for actual
checks, limitations and the resolved failed-build residue.

## Decision 110: read-only physical plugin schema inspection (2026-10-20)

Continue step 03 by comparing actual website-owned MSSQL catalog metadata with
the existing logical MigrationSchemaFootprint. A private Kernel/Plugins service
checks administrator plugins.migrate before lazy I/O; Bootstrap supplies a
focused Singularity handler through Order, without coupling the two private
Kernel owners or exposing a public endpoint/SDK. Expected schema is trusted
composition input; requests cannot replace identity or connection details.

The mssql-simple-v1 profile supports bounded plain dbo tables, exact scalar
types/widths/nullability, binary text collation and one ordinary clustered PK.
Unsupported physical flags, extra objects/dependencies and unknown SQL profiles
refuse. Use a separate dbo operator connection because per-object DENY can hide
metadata from restricted readers even with VIEW DEFINITION. No grants or runtime
elevation occur. Fixed prepared catalog SELECTs use ASCII parameter typing and
hex identifiers; two matching scans and checked rollback provide a read-only
observation, not an atomic DDL snapshot or execution authority.

Offline fault/authority/composition cases and the fresh marked SQL lab verify
the boundary. Actual ODBC testing exposed an implicit wide-parameter byte-length
failure; the ASCII namespace parameter is explicitly VARCHAR. It also exposed
retained LOB storage after removing a MAX column: the inspector continues to
refuse that residue; only the synthetic test table is rebuilt by fixture code.
Frozen contracts, journals, production DDL and ordinary website bindings remain
unchanged. Installed-state history, executor/recovery, provisioning and live
folder-plugin lifecycle remain pending. See docs/PLUGIN_SCHEMA_INSPECTION.md
and STATE for precise evidence and limitations.

## Proposed decision P105: independently versioned Main/Game/Database/Schema APIs (2026-10-19)

**Status: proposed documentation design only; runtime unimplemented.** Under one trusted core, define versioned `MainAPI`, `GameTypeAPI`, `DatabaseTypeAPI` (optional external game transport only) and `SchemaAdapterAPI` (verified schema/emulator decoding). ## Proposed decision P104: physical folder plugin architecture (2026-10-19)

**Status: proposed, design documented; no code/runtime execution.** The end-state
moves from only statically composed PHP modules to a trusted folder-discovered
`plugins/<id>/` runtime. Folder presence controls *whether executable code exists*
in the next request, while website-owned MSSQL controls approval, activation,
licensing, settings and migration history. Removing the folder removes all plugin
contributions non-destructively; core and unrelated plugins keep running;
reintroducing an approved compatible folder may restore saved state. New plugin
code does not auto-run before trust approval. Dynamic registrations consume new
versioned `PluginAPI` contracts without rewriting frozen V1-V5; saved GrapesJS
projects use safe missing-provider placeholders. Distinguish physical folder
installation from visual GrapesJS drag-and-drop. See `PLUGIN_SYSTEM.md`.

Use a **provisional ID** instead of falsely inserting this as an already executed
numbered implementation decision after the repository's existing history. The
real agent must allocate the next available decision ID during implementation,
