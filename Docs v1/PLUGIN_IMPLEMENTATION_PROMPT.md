### Constraints

- Existing code is contract-based. Favor additive versioned contracts, no hardcoded global plugin names, no immutable-static manifest list requiring human edits for each plugin.
- The user wants **copy folder to install, remove folder to deactivate immediately on next request, without breaking the website**. That behavior outranks architecture ceremony but never outranks trust, authorization, data-integrity or native game safety.
- All website configuration authoritative in website-owned MSSQL. Physical folders determine code presence. Removal never deletes plugin data or any game data.
- Preserve separate AdminCP authority, secure CSRF/auth, server-side capability checks, player/game actor isolation, license gates, and guarded game/payment mutations.
- In-process PHP plugins are trusted code, not a sandbox. State limitations accurately; isolating arbitrary hostile PHP requires separate processes.
- An explicit authorization to continue implementation is documented for Phase 4, but do not treat it as permission to run production SQL, mutate active game data, use legacy runtime, erase files or deploy.
- If the complete change is too large, implement the **first end-to-end plugin slice** with honest tests now rather than producing only abstract directories/interfaces; leave truthful staged work in `STATE.md`.

**Definition of done:** A real tested `plugins/zenda.example` package can be physically added, removed, and re-added without editing core or restarting the server; every registered surface reacts correctly; unaffected core/other plugins still pass; plugin data persists; approvals and failure modes fail closed; test evidence is documented.
